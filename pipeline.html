Delivery pipeline · agent-fleet v0.1.0

Agent Fleet Pipeline

Seven role agents and twenty-six skills carrying a client brief from the first call to shipped modules. Modules ship one at a time in dependency order — throughput is not the goal, consistency is. Module 7 must look like module 1.

7 agents 26 skills 16 stages 8 human gates 1 parallel branch

The three rules everything else is procedure

Agents have no memory between runs. A human colleague carries the client call in their head; an agent starts blank every invocation. These three rules are what replace that.

M.0 preamble

Every agent reads inventory.md before doing anything. No exceptions. Skipping it is how the same component gets built twice.

Reuse plan is binding

Every module spec classifies each capability as reuse, extend, or new against the inventory. Every new carries a justification, or the gate rejects it.

Rule of two

Nothing becomes shared on first use — anticipated abstractions are shaped wrong. Entities are the exception: migrating a table across shipped modules costs far more than moving a component.

Phase A · Foundation once per project

The global layer is not frozen all at once — you cannot know every shared entity before building. What freezes here is the smallest thing that lets modules fan out safely: tokens, primitives, shared entities, and a runnable shell.

F.0
product-owner
requirements-intake
Client input becomes 00-global/requirements.md — stated vs assumed vs open, kept separate. Explicit out-of-scope.
Gate · Client Open questions answered. Boundaries that affect module shape must resolve here.
F.1
product-owner
module-decomposition
Entity-dependency graph, topological sort, ordered queue with one line of reasoning per position. Nothing is hardcoded into first place — auth usually lands there because most entities reference a user, but that is derived.
Gate · You Approve or edit the order: list. A wrong order costs rework on every module after it.
F.2
system-architect
service-design
Services, boundaries, cross-cutting owners, decisions with rationale. Error shape and pagination style are decided here, once — deferred, they get re-invented by every module.
Two independent chains
F.3
ux-engineer
design-system
Semantic tokens: color, type, spacing, radius, elevation, motion, focus, z-layers. Dark mode decided now, even if the answer is no.
F.4
ux-engineer + frontend-builder
component-library
Roughly 10–12 primitives, each with full variant, state, and accessibility coverage. No domain components — rule of two governs those.
F.5
backend-builder
foundation-schema
Entities referenced by two or more queued modules. Identity, timestamps, soft delete, tenancy, and audit decided once for the whole product.
F.6
backend-builder
project-skeleton
Repo layout, routing shell, DB connection, migration runner, validated env config, error middleware, test harness, green CI.
Gate · You Foundation frozen. Seed inventory.md with primitives, entities, and the patterns decided at F.2.

Phase B · Module loop repeat per module, in queue order

Serial delivery means each module ships demo-able, later modules learn from earlier ones, and a contract amendment is cheap because only one module is ever in flight. The cost is throughput — which is why the reviewer at M.8 matters more here than it would anywhere else.

M.0
every agent
Read 00-global/inventory.md. Mandatory preamble in every agent's prompt.
M.1
product-owner
write-brd
Nineteen edge-case dimensions worked line by line: validation, permissions per role, ownership, concurrency, quotas, data lifecycle, bulk partial failure, side effects, time, import/export, offline. Acceptance criteria in Given/When/Then.
Gate · Client Scope and acceptance criteria approved.
M.2
system-architect
groom-module
Technical spec plus the reuse plan — every capability classified against the inventory. This table is what stops a serial pipeline producing seven applications wearing a trench coat.
Gate · You Challenge every new verdict. If most rows are new by module 4, the inventory is not being read.
M.3
backend-builder
schema-design
Module-owned tables. Shared entities referenced, never shadowed. Runs before the contract so schemas are grounded in real tables.
M.4
ux-engineer
design-direction
Two artifacts, both required: a canvas for you and the client, and design-spec.md for the builder — token names, component verdicts, every state, breakpoints, data binding, real copy.
Gate · You + Client Review the canvas.
M.5
system-architect
api-contract
Reads the data model so schemas describe fields that exist, and the design spec so endpoints return fields the screens need. Every error specified. Examples realistic — mocks are generated from them.
Gate · You Contract frozen. This gate is the only reason the next stage can run in parallel.
Parallel — the pipeline's only concurrency
M.6a
frontend-builder
read-design-spec build-component compose-page wire-api-client
Builds against mocks generated from the contract — success, empty, multi-page, every specified error, and slow.
M.6b
backend-builder
migrations api-endpoint auth-authz
Reversible migrations, handlers matching the contract exactly, an explicit authorization decision on every endpoint including the ones that look public.
↺
system-architect
amend-contract
The escape hatch. A blocked builder never works around the contract locally — the change is logged, examples updated, both sides notified, contract re-frozen.
M.7
integrator
swap-mocks e2e-verify
Reconcile before wiring: diff the contract, the backend, and the frontend. Divergences are resolved by fixing a side or amending — never by a translation shim. Then the BRD's acceptance criteria become the e2e suite.
M.8
reviewer
drift-check promote-shared
Consistency, not correctness — /code-review handles bugs. Duplicated components matched by behaviour rather than name, hardcoded values, endpoint convention drift, shadowed entities. Verdicts: promote, refactor, accept.
Gate · You Ship and demo to the client.
M.9
reviewer
close-module
Writes summary.md (detail) and folds it into inventory.md (index, one line per item). The Patterns section is the valuable half — it is what prevents a second pagination style in module 5.
↺  Next module in the queue starts at M.0 by reading the inventory just written. That read is the entire payoff of M.9.

Agents role = context boundary · skill = procedure

One agent per role, many skills each. The agent boundary is what must be held in one head at once — building page three requires remembering the components built in step one. Splitting further just causes context thrash.

product-owner

opus

Business truth. Requirements, module decomposition, BRDs. Names no technology — a constraint is recorded as a constraint, never as a solution.

requirements-intakemodule-decompositionwrite-brdclient-brief

system-architect

opus

Technical boundaries and contracts. Owns the boundary object both builders consume, and the only sanctioned way to change it.

service-designgroom-moduleapi-contractamend-contract

ux-engineer

opus

Design system and per-module design intent. Always emits both a canvas and a spec — either alone leaves the builder guessing.

Before first use, fill in CONVENTIONS.md: stack, repo layout, naming, API and frontend conventions, testing, git. Agents read it before writing code, and any field left as TBD becomes a question they must ask rather than a guess they will get wrong.
